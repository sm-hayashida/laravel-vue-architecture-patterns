# 07. DDD 戦術的設計 (Tactical Design)

## 概要
ドメイン駆動設計 (Domain-Driven Design, DDD) は、ビジネスロジックを中心に据えたソフトウェア開発手法です。戦術的設計は、ドメインモデルを実装コードに落とし込むための具体的なパターンを提供します。

本プロジェクトのテーマである「在庫管理」を例に、主要なパターンを解説します。

---

## 主要な戦術的パターン

### 1. 値オブジェクト (Value Object)
- **定義:** 属性（値）の組み合わせによって識別されるオブジェクト。
- **特徴:**
    - **不変性 (Immutability):** 一度作成されたら変更されない。変更は新しいインスタンスの作成で行う。
    - **交換可能:** 同じ値を持つインスタンスは同一とみなされる。
    - **自己検証:** コンストラクタで自身の正当性を保証する。
- **在庫管理での例:** `Quantity`（数量）, `Sku`（商品管理番号）, `Price`（価格）。
- **メリット:** 「0以下の在庫数」といった不正な状態がシステム内に存在することを防ぐ。

### 2. エンティティ (Entity)
- **定義:** 一意な識別子（ID）によって識別されるオブジェクト。
- **特徴:**
    - **同一性 (Identity):** 属性が変化しても、IDが同じであれば同じものとみなす。
    - **可変性:** ライフサイクルを通じて状態が変化する。
- **在庫管理での例:** `Product`（商品）, `Stock`（在庫点）。
- **メリット:** 商品名の変更や在庫の増減を、同一の対象に対する変化として追跡できる。

### 3. 集約 (Aggregate)
- **定義:** 強い整合性を維持すべきエンティティと値オブジェクトのまとまり。
- **特徴:**
    - **集約ルート (Aggregate Root):** 外部からは集約ルートを通じてのみ操作を許可する。
    - **整合性の境界:** トランザクションは集約単位で管理する。
- **在庫管理での例:** `Product` をルートとし、その属性としての `Price` や `Stock` を含む。
- **メリット:** 複雑な関連を持つオブジェクト群の状態を、常に矛盾なく保つことができる。

### 4. ドメインサービス (Domain Service)
- **定義:** エンティティや値オブジェクトに記述するのが不自然な、複数のオブジェクトにまたがるビジネスルール。
- **特徴:**
    - 状態を持たない（Stateless）。
    - 濫用するとドメインモデルが貧血症になるため、まずはエンティティ等に書けないか検討する。
- **在庫管理での例:** `StockTransferService`（在庫移動サービス：A倉庫からB倉庫への移動処理）。

### 5. リポジトリ (Repository)
- **定義:** 集約の永続化（保存）と取得を担当するインターフェース。
- **特徴:**
    - ドメイン層ではインターフェースとして定義し、インフラ層で実装（DIP）。
    - 開発者には「メモリ上のコレクション」のように見せる。
- **在庫管理での例:** `ProductRepositoryInterface`。

## なぜ戦術的設計が必要なのか？

### ドメインモデル貧血症からの脱却
MVCパターンの Model（Eloquent等）は、データ構造と永続化に特化しがちで、ビジネスルールが Controller や Service に漏れ出します。
戦術的設計を用いることで、**「データ」ではなく「振る舞い」**に注目した設計が可能になります。

| 特徴 | ドメインモデル貧血症 (MVC等) | 豊かなドメインモデル (DDD) |
| :--- | :--- | :--- |
| **ロジックの場所** | Controller / Service | Entity / Value Object |
| **バリデーション** | Requestクラス等で外部から実施 | オブジェクト内部で常に保証 |
| **可読性** | `if ($stock > 0)` (手続き型) | `$stock->canShip()` (宣言的) |
| **テスト** | DB接続等が必要な統合テスト寄り | 純粋なロジックの単体テストが容易 |
